# 第 9A：证据采集与门禁绑定

2026-10-17：按用户选择的 **A** 实施。配置模式的测试门禁只接受平台实际执行的集成候选验证；代码评审和业务验收由对应独立人工角色提交说明。门禁证据已接入工作台、治理命令、验收、人工合并建议及计划基线准入。2026-10-18 已由 [9C 审计导出](audit-export.md) 接续历史关系；候选与验证读取同时核对 scope/kind。

## 已交付的存储约束

- 内容以 JSON 对象追加，单份内容上限 64 KiB，嵌套深度最多 32 层。对象字段排序后规范化；数组顺序保留。内部 JSON 映射采用无损十进制读取，避免高精度指标在存取后改变摘要；不修改全局映射设置。
- 每份证据绑定计划指纹、任务 ID、执行 ID、真实提交 SHA，以及 context/API contract/DB schema/ADR 版本。存储层检查格式；采集时由服务端当前运行时提供绑定，并核对真实 Git 提交。请求必须指定当前 `taskExecutionId` 和 `commitSha`，避免上一轮执行的延迟审批落到新执行上。
- SHA-256 覆盖绑定、作者、类型、操作键、创建时间和内容，作为证据 ID。读取及幂等重试重新核验内容与元数据摘要。
- 幂等键按计划隔离。同键、同绑定、同作者、同内容返回原记录；内容、绑定、作者或类型变化均拒绝。数据库唯一约束防止同键竞争插入两条记录。
- 无应用更新/删除接口。调用方修改传入或返回的 JsonNode 不会改变已持久化内容。未知 ID 或跨计划读取拒绝，原记录保留。

摘要校验只能证明已存字节与引用一致，不能证明作者的陈述真实，也不能证明测试确实执行。它不是数字签名，不能抵抗拥有整个数据库写权限且能同时修改所有引用的人。当前没有对外暴露任意作者或证据类型的写入接口。

## 采信边界与操作流程

1. 开发者提交真实任务分支后，独立工程负责人进入评审，使用 `statement` 提交代码评审说明。
2. QA 进入测试。工程负责人创建包含该任务及完整依赖闭包的候选，独立 QA 执行批准计划中的验证方案。
3. QA 为 UNIT_TEST / INTEGRATION_TEST 门禁指定候选 ID 与最新验证 ID。通过审批要求验证已完成且为 PASSED，全部检查的命令、工作目录、退出码、超时及截断状态均符合批准方案。拒绝审批要求对应 FAILED 结果；RUNNING/ABANDONED 不能放行。
4. 独立业务审批人提交说明，并在四项有效证据齐全后验收。工程负责人只能获取人工合并建议，平台不合并 main。

| 门禁 | 必填证据字段 | 证据内容 |
|---|---|---|
| CODE_REVIEW / BUSINESS_ACCEPTANCE | `statement`，非空且最多 16000 字符 | 本人说明、结论、主体及精确执行绑定 |
| UNIT_TEST / INTEGRATION_TEST | `candidateId`、`validationId` | 最新平台验证引用与完整结果摘要，包括实际检查输出 |

平台证明批准命令实际执行及结果一致性；命令是否充分覆盖单元、集成及业务要求，仍由计划审批和 QA 判断。两类测试门禁可复用同一次批准方案验证，并不自动把任意成功命令认定为充分测试。HTTP `SUCCEEDED` 摘要、外部 CI URL、手工“测试通过”文字均不能代替平台验证。外部 CI 签发者与验签不在已选 A 的范围。

## API 与重试

通过 `POST /api/v1/governance/commands`，使用个人 Bearer 凭据。采集与记录门禁属于同一个持久命令，不需要先调用额外写入接口：

```json
{"action":"record_gate","taskId":"TASK-1","taskExecutionId":"<当前执行 ID>","commitSha":"<当前完整 SHA>","expectedVersion":1,"idempotencyKey":"review-001","gate":"CODE_REVIEW","passed":true,"statement":"已核对提交差异，说明核对范围与结论。"}
```

```json
{"action":"record_gate","taskId":"TASK-1","taskExecutionId":"<当前执行 ID>","commitSha":"<当前完整 SHA>","expectedVersion":1,"idempotencyKey":"test-001","gate":"UNIT_TEST","passed":true,"candidateId":"<候选 ID>","validationId":"<该候选最新验证 ID>"}
```

成功返回 `recorded: true` 和 64 位 `evidenceRef`。也可用已有 `evidenceRef` 替代新证据字段，但只接受同计划、同任务/执行/提交/版本、同门禁/结论、同本人且仍有效的证据。不能混用已有 ID 和新内容。`GET /api/v1/evidence/{id}` 只向当前项目成员提供当前计划的证据读取，无应用更新/删除 API。工作台显示各门禁证据 ID。

采集的证据和门禁投影随命令日志恢复；结果未知时保留原请求与幂等键核对，不创建重复审批。同键完成重试返回原操作事实，不代表重新签发当前有效资格；验收和合并建议仍独立复核。

## 失效与兼容

开始测试、验收、合并建议和候选基线准入均重查证据内容、当前版本、真实提交、候选指纹和最新验证结果。新一轮验证会使旧测试门禁证据失去放行资格，即使任务仍显示 ACCEPTED。QA 可在已验收状态更新通过证据；这不改写历史验收，也不允许用失败结果续签。重试/语义重验证清除当前门禁引用，旧证据仍保留。

历史配置模式的自由文本引用不会自动升级为证据；缺少内容或绑定时拒绝放行。TESTING 阶段可重新提交已通过代码评审的说明，ACCEPTED 阶段可重新提交各项通过证据。旧 demo 模式保留自由文本兼容，用于演示，不能作为本阶段证据门禁验收。

本阶段为单节点平台内可信采集；摘要不构成外部签名。运行时重建与待完成命令恢复的验证不等同于操作系统断电或多节点耐久性认证。最终验证记录见 [当前状态](status.md)。
