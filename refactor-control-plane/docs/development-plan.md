## 修正原计划

- 多执行者协作是主线。文章多用户编辑、跨请求幂等归入样例行为要求，按验收需要处理，不再排在核心执行闭环之前，也不单独无限扩展成博客产品。
- 不等待客户生产数据库备份来推进平台。固定样例已有 SQL 数据；真实数据库引擎兼容检查使用隔离夹具，客户环境验证属于后续具体项目交付。
- 完整博客的用户、评论、菜单改造不自动加入首个文章切片。与文章相关的访问权限、关联、旧路由、富文本行为必须明确保留或替代策略；改变已有行为需要业务确认。
- 分离平台元数据与被管控项目业务数据。已按用户选择 A 拆分独立进程和数据库；旧共用 H2 路径仅保留 demo 兼容，配置模式不初始化业务表。
- OIDC/LDAP、多节点数据库和租约、生产连接器单列后续路线，不计入单节点 v0.1 收尾。平台统一 ETL、跨库分布式事务和全语言深度分析均不是由现有验收自然推导出的必做项。

## 迁移数据的三个边界

| 数据 | 归属 | 当前存放/来源 | 计划中的职责 |
|---|---|---|---|
| 执行日志、任务恢复事件、集成候选、验证结果 | 控制平台 | H2 `data/control-plane`，如 `audit_event`、`integration_record` | 平台负责权威流程状态、授权及证据；未来换受管数据库是平台自身存储升级 |
| 旧文章标题、正文、路由、菜单关联和时间 | 被升级的 SpringMvcBlog 项目 | 固定提交中的 `Blog/src/main/resources/db/blogdb.sql`，旧 MySQL `posts` 表 | 作为文章迁移输入；并非平台历史任务数据，也不是已连接的客户线上数据库 |
| 新文章与旧新 ID 映射 | 被升级项目的新业务实现/迁移工具 | 独立样例 H2 的 `modern_articles`；历史 demo 保留 `legacy_post_import`、`article_migration_run` | 归业务目标和迁移运行所有；第 10 里程碑按选定引擎完成独立迁移工具，平台只接收验收证据 |

历史 demo 迁移服务共用 Spring `JdbcTemplate`，读取同一个 H2 的 `posts`，事务写入文章、映射和迁移记录。测试从固定 Git 对象提取 posts INSERT 并在测试 H2 重放；没有通过 MySQL 驱动读取旧库。已验证数据映射不等于已经验证 MySQL 的字符集、驱动、事务与恢复行为。

“真实 MySQL 验收”应拆为：① 固定样例在隔离数据库引擎上的兼容证明，属于本次样例验收；② 某个客户真实业务库的脱敏数据、备份恢复、停写/切换及性能验证，只有接入该项目时才进入交付范围。其他被管控项目可使用 PostgreSQL、其他存储或完全不迁库，平台不强制迁移 MySQL。

| 决策 | 选项 A | 选项 B | 决定时点 |
|---|---|---|---|
| 样例与平台的物理隔离 | 独立样例应用/数据库，由平台调度验收。边界清楚、最能证明平台能力，但增加启动和部署配置；推荐用于完整示范 | 保留同一应用的演示模块，使用独立数据源与测试配置。开发成本较低，但必须证明平台核心无文章依赖，且清楚标注运行隔离的局限 | 第 7 里程碑确定样例目标布局前 |
| 文章数据升级策略 | 保留 MySQL，在独立样例库中扩展兼容结构并验证旧数据可读。减少同时变更数据库的风险，适合证明框架升级 | 迁到新的目标库，通过快照/导入/映射验证新旧对照。能验证数据库迁移，但新增字符集、SQL 方言、切换恢复范围，适合确有更换数据库目标时 | 第 10 里程碑数据库实施前；需明确目标引擎/版本 |
